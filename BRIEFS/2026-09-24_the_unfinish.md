## The law to build

1. ONE WORD, ONE CONTROL. Every completed item on every Complete pane (trim, pasteurization, prepack) carries `<` titled `Unfinish`, with the Admin PIN field today's Demote carries (`name="unfinish_pin"`), posting `POST /production-scheduling/<stage>/unfinish/<id>`. The scheduling surfaces' `/demote/<id>` route and the word Demote retire there (the Data Queues' generic Demote is another act and stays). The row returns complete to scheduled with `completed_at` and `completed_by` cleared, logged under a new `SYSTEM_REASON.schedule_unfinish`. A wrong PIN refuses as today (`SCHEDULE_REFUSAL.demotePin`, reworded to Unfinish).

2. CHECK EVERYTHING, THEN WRITE ONCE (his pick). Every unfinish reads the next process's records before it writes; a worked record refuses the whole act with words that name it (the run, the output's tag, the file), and nothing is written on a refusal; on success one `db.batch` carries every statement, each row logged under the actor the PIN admitted.

3. TRIM. The next process is pasteurization. If a run on the same HBN stands scheduled with no outputs entered, the unfinish unschedules it exactly as `Unschedule` on that run does today (the run row soft-deleted with `SYSTEM_REASON.schedule_unfinish` as its delete reason, its containers free for another `>>`), and the flash says so (`Unfinished; the pasteurization run on <hbn> was unscheduled.`). A scheduled run with outputs refuses (`The run on <hbn> has <n> outputs entered; void them or unfinish the run first.`); a finished run refuses (`The run on <hbn> is finished; unfinish it first.`). No run: the row alone.

4. PASTEURIZATION, THE RUN. The next process is testing. The unfinish returns the run to Working as it stood before its lines: the run complete to scheduled; every input container the finish consumed returns pasteurized to cryo_queue by a new transition `cryo_unconsumed` (from pasteurized, to cryo_queue), its child ledger item's grams restored to the container's `weight_grams` (`setItemQtyLocationStmts` with the reason); every output the run bore is voided with its ledger item (the two `deleted_at` rows and their log rows, `SYSTEM_REASON.schedule_unfinish` the reason), so the Testing Queue loses them and the pool reads whole again. Refusals, each naming the record: an output whose status is not testing_queue (released, packed, gone); an output with a `test_samples` row; an output whose tag stands in a marked `test_sample` upload; the run's New Packages file marked uploaded (`metrc_uploads` kind new_packages, `ref_id` the run); a container whose child item was moved or drawn since the finish (its item not at 0 g, or voided). The flash: `Run unfinished; <n> containers back in the Cryo Queue, <m> outputs voided.`

5. PASTEURIZATION, ONE AT A TIME (his pick "Both, one at a time"). On the finished run's page at Cryo Weight Entry (`src/cryo.ts`): each consumed container in the pool list carries `<` Unfinish (PIN): pasteurized to cryo_queue by `cryo_unconsumed`, its child item's grams restored, its `cryo_run_inputs` row removed so the pool by category shrinks (the over-issue flag reads the new pool and flags, never blocks, as 0.30.121 rules); refused while the run's New Packages file is marked uploaded (its ingredients would no longer match METRC) or the run is scheduled (Unschedule frees a working run's containers). Each output row carries `<` Unfinish (PIN) in place of the void link today: the output and its ledger item voided together, its grams back to the pool, logged; refused when the output is released, packed, gone, sampled, or in a marked upload (test_sample or the run's new_packages). On the Testing Queue, the generic Demote on a package with `source` cryo becomes this output unfinish (PIN through the queue control as the void page asks it) instead of a status step to a queue it never came from; a trim container's Demote stays as it is.

6. PREPACK. The next process is the METRC upload lane. The unfinish on a finished pack: the job complete to scheduled; the parent package packed to released by a new transition `prepack_unpacked`; the parent's ledger grams restored to what the finish zeroed (the finish's own log row on the item's `qty`, `old_value`, under the reason `prepack finish...`); the carry the finish opened is voided when untouched (`status` open and `remaining` equal to `grams`), refused when drawn (`The carry of <g> g was drawn by <job>; unfinish that job first.`); refused when the job's `package_finish` or `new_packages` file stands in a marked upload. The lines and their FG items stand as entered (they were born at the line); the pending files leave Pending Data Uploads by the job's status, as `listPendingPrepackFiles` reads it. The flash: `Pack unfinished; <tag> back to released with <g> g.`
