## The law to build

1. THE BOX ON EVERY ROW. On both pages every row that has a per-row action gains a leading checkbox cell (`<input type="checkbox" name="id" value="<row id>">` on Data Queues; `name="item" value="<kind>:<id>"` on Pending Data Uploads, the kind and id exactly as the per-row form posts them today, so a manifest rides `manifest:<movement id>`, a location move `location_move:<group id>`, a wet weights file `wet_weights:<batch id>`). The reconcile notes get no box; they have no file and keep `Acknowledge`. Rows that refuse today keep refusing: a Logistics Move with receipts shows its box disabled with today's words beside it.

2. THE CHECK-ALL. Every section's table head gains a checkbox in the leading cell that checks and unchecks every enabled box in that section (and only that section); it reads indeterminate when some are checked. A grouped queue (rows under `<h3>`s) has one check-all per section, over all its groups. The script is inline, small, and does nothing a page without script would break: without it the boxes still post.

3. VOID THE CHECKED, ONE REASON (his pick). Each Data Queues section (the seven queues and Logistics Moves) becomes one form, `POST /admin/queues/<queue key>/void-checked` (Logistics Moves posts `/admin/queues/movement/void-checked`), carrying the checked ids, a required `reason` typed once, and the actor as every form carries it. The action voids every checked row through the same path today's `Void` takes (`voidRecord` per pipeline row, `voidLogisticsMove` per movement), so every guard holds and every row lands in `record_change_log` as today's void lands it, the one reason on each. A refused row refuses the whole batch before anything is written: check every id first (the table, the guards, the receipts), then write; the refusal flash names the row. The button reads `Void checked (n)` with n live and is disabled at 0; the redirect is `/admin/queues?ok=voided&n=<n>` and the flash `Voided n.` The per-row `Edit`, `Void` and the queue's row controls stay exactly as they are; the row controls are not batched (his pick took the first option, not the second).

4. MARK THE CHECKED UPLOADED (his pick). Each Pending Data Uploads section becomes one form, `POST /admin/uploads/uploaded-checked`, carrying the checked `item` values and the actor. The action resolves each `kind:id` exactly as `POST /admin/uploads/:kind/:id/uploaded` resolves it today (the same `markUploaded` calls with the same kind constants from `METRC_UPLOAD_KINDS`, the wet weights, manifest, location move, test sample and prepack special cases included) and writes them in one `db.batch`, so a checked file is recorded uploaded to METRC, never cleared. The button reads `Mark checked uploaded (n)` with n live and is disabled at 0; the redirect `/admin/uploads?ok=uploaded&n=<n>` and the flash `Marked n uploaded.` `Clear all pending` stays as it is (cleared, not uploaded), and so does every per-row `Mark uploaded` and `Download`.

5. THE FOLD, OPEN ON LOAD, REMEMBERED (his pick). Every section heading on both pages becomes the `<summary>` of a `<details class="queue-fold" data-fold="<key>" open>`: the queue key on Data Queues (`logistics_moves` for the moves), the data type on Pending Data Uploads (`wet_weights`, `manifests`, `location_moves`, `reconcile_notes`, the others by their kind word). The count stays in the summary so a folded section still says how many wait. Every section renders open; the inline script reads `localStorage["gf_fold:" + location.pathname]` (a JSON array of folded keys), closes those on load, and writes the array on every toggle. The `Clear all pending` reveal keeps its own `<details>` and its own behavior. The existing `data-pipeline-key` and `data-count` attributes stay on the heading so the tests and the smoke that read them keep reading.

6. THE WORDS. Spanish on every new string in `src/i18n.ts`: `Check all`, `Void checked`, `Mark checked uploaded`, `Nothing checked.`, `Voided n.`, `Marked n uploaded.`, the reason placeholder if a new one is made, the refusal that names a row.
