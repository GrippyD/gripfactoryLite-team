## What GRIPCasting is
Finance's rolling cost forecast and revenue driver model for the 2026 harvest year (April 2026 to March 2027): finance loads monthly actuals from the BU Summary workbook and sets revenue drivers; BU directors build and submit line item forecasts; finance makes the final submission; the app shows cost landing vs budget, EBITDA, build progress by BU, and the QuickBooks back up transactions behind each line. As shipped it is a Vite browser app plus a Cloudflare Pages Functions API on Supabase Postgres. Its source is vendored, unserved, under `app/vendor/gripcasting/` (src/shared, src/server, src/web, index.html, tests, the Postgres migration and the import script, as reference; its bytes are the reference, so its dashes stand there; anything you write in GFLite follows G-8).

## The law
1. THE PLACE. A new tile "GRIPCasting" on /models (MODEL_TOOLS in src/config.ts learns an app kind beside the vendored slugs). The app lives at `/models/gripcasting/` and its API at `/models/gripcasting/api/*`, both behind the Models PIN gate that already guards `/models/*`.
2. THE MODEL STAYS THEIRS. `vendor/gripcasting/src/shared/model.ts` and `types.ts` move into `src/gripcasting/` UNCHANGED in logic (dashes in comments or strings replaced, nothing else). The model is the finance team's: no rounding, rule or formula changes. Its tie-out test (vendored as `tests/model.test.ts.ref` so vitest never picks it up) comes along and still skips without finance's fixtures; with them every difference must be $0.00.
3. THE DATA ON D1. Migration 0103 carries the 15 tables as `gc_` tables (gc_app_users, gc_harvests, gc_business_units, gc_gl_accounts, gc_budget_lines, gc_drivers, gc_actual_closes, gc_actual_lines, gc_actual_monthly, gc_transactions, gc_upload_log, gc_builds, gc_build_lines, gc_build_items, gc_submissions) with: TEXT ids (uuid strings), money as INTEGER cents for numeric(12,2) and INTEGER ten thousandths for numeric(12,4) unit rates (converted at the query edge so the model sees the same dollars), ISO text for timestamptz and dates, TEXT JSON for jsonb, the same natural keys (GL and BU names within a harvest), the same uniqueness, created_at/updated_at and created_by on every table, optimistic locking kept (the version the API checks). Indexes for every read the API makes. The migration writes no business row.
4. THE API. `src/gripcasting/routes.ts` and `queries.ts` port the nine endpoints exactly (GET me, reference, state, actuals, actuals/{date}, transactions, submissions/{id}/snapshot; PUT drivers, builds/{code}; POST actuals, submissions) as Hono routes in GFLite, SQL rewritten for D1 (multi statement writes in `db.batch`, at most 100 bound parameters a statement, chunk big uploads such as transactions). Request validation ported from validate.ts. Error shapes and status codes as theirs.
5. WHO MAY DO WHAT. Identity is GFLite's own (the Cloudflare Access email GFLite already trusts, the same way every GFLite page reads it); the vendored JWT verifier (auth.ts) is not ported. Role from gc_app_users (active row: admin = finance, director); no row or inactive means 403 on every API call, even past the Models PIN. Admin only: load actuals, change drivers, final submission. Directors edit and submit BU builds and read everything (their business decision). created_by, edited_by and submission authors come from the identity, never the request body. The Models PIN is the outer door; the role table is the real one.
6. THE BROWSER APP. The vendored `src/web` becomes a static app under `public/models/gripcasting/` (index.html, app.js, styles.css), served the way the Harvest Menu Tool is (no-store, behind the gate). Its fetch base becomes `/models/gripcasting/api/`. Bundle it with the esbuild GFLite's own wrangler already brings (a `scripts/build-gripcasting.mjs`; no new npm dependency without the owner's word), and commit the built files so a push to main deploys them with no new CI step; the smoke pins their bytes. SheetJS stays loaded on demand from cdnjs exactly as the vendored parse.ts does. No business figure in any served file: everything comes from the API.

THE DATA LOAD (the owner's hands, production data). `scripts/gripcasting-import.mjs`, ported from the vendored import.ts: reads finance's `const.json` and `data/` from a folder OUTSIDE the repo (default `../db_backups/_imports/gripcasting/`, git ignored), takes `--admin email=Name` and `--director email=Name` pairs, and loads harvests, BUs, GLs, budget, wages budget, seasonal pattern, default drivers, current actuals, BU builds and users through the same D1 path `scripts/repair-apply.mjs` uses (reuse `scripts/d1lib.mjs`), refusing to run against remote without `--remote`, all or nothing (stop at the first failure, report what loaded), never printing figures. A `--dry-run` that only counts rows.

## Performance
Reads are small (one harvest year); the state endpoint is one round of indexed reads in parallel; an actuals upload of a few thousand transactions goes in chunks. The Scribe times every endpoint and the app's first load on a bench with a synthetic year (no finance data in the cloud); nothing over 1 s.
