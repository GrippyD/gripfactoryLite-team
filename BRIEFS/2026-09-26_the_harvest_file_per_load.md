## The ruling (owner, 2026-09-26, verbatim)

His question first: "For split batches where there's a lot spread over two loads, does it produce one csv or two?"

Then the METRC rule: "Apparently when we do this, in METRC we can append a csv and then another of a different name that points at the same HBN, as long as I don't finish the HBN in METRC, I can upload multiple csvs to it.  So we do HBN(1), HBN(2) and so on (the actual HBNs, not the text "HBN") for the csv names.  The point is, when one lot is split over two truck loads, the HBN stays in common, but it gets a package tag in METRC for each upload.

We need our CSV flow to reflect this"

His picks on the question tool, verbatim: a lone load's name "HBN(1).csv always (Recommended)"; the plant tags "Paste tags per load"; a load changed after its upload "Flag it, no re-pend (Recommended)"; the load's other files "Yes, match the (n) (Recommended)".

## What the Scribe read

1. THE HARVEST FILE TODAY (`PENDING_WET_UPLOADS_SQL`, `listPendingUploads`, `listWetWeightUploadReads`, `listWetWeightUploadEntries` in `src/db.ts`; the route `GET /admin/uploads/wet_weights/:file` in `src/index.ts`; `wetWeightsFilename` in `src/csv.ts`): one file per HBN, `<HBN>.csv` (owner ruling 2026-08-31), carrying every finished load of the batch. It pends while the newest `updated_at` of the batch's finished loads is newer than its latest `wet_weights` mark, so a second load re-pends the batch and the new file repeats the first load's rows, and any later change to a load re-pends it too, its unload and trim status moves included (they bump `updated_at`). The mark (`markUploaded`, `planUploadMark`, `markCheckedUploaded`, `clearAllUploads` in `src/actions.ts`) is batch-level with `ref_id` NULL. The sheet sync's `pendingHarvestFile` (`src/sheetsync.ts`) reads the same law and names `<HBN>.csv`. A throwaway probe on a copy of the live tree (2026-09-26) showed it: load 1's file marked, then load 2 finished, and the file came back with 600, 400 and 500, load 1's rows again.

THE TAGS TODAY: `harvest_plant_tags` per batch (migration 0012), pasted on the Wet Weights row (`savePlantTags` replaces the batch's tags), split across every finished load by weight (`allocateTagCounts`, `splitPlantWeights`, seeded by the batch id), so a second load moves tags that rode the first load's file. The 2026-09-25 snapshot holds 23,572 live tags on 33 batches and 39 loads, no batch with two loads.

4. THE DATE: the file's ActualDate reads the load's `updated_at` (the provisional rule of 2026-08-31), which moves with every later change; the load's `effective_date` (migration 0053, canon 0.30.94: "It's always the source data for the transaction date") holds the weigh-in's business day.

## The law to build

1. THE LOAD'S NUMBER. Each load of an HBN carries a number, 1, 2, 3, in the order its loads first finish: a new column `wet_weight_entries.harvest_file_seq`, set when a load first leaves weighing to one more than the highest number in its batch (voided loads counted, a number never reused), kept through an unfinish and a re-finish; a load re-pointed to another HBN takes the next number there. The migration backfills every existing load, per batch, by `created_at` then `id`. A NULL (a load a repair wrote) reads as its rank by `created_at` then `id` among its batch's loads, voided ones included.
2. ONE HARVEST FILE PER LOAD, `<HBN>(n).csv`, a lone load included (his word: "HBN(1).csv always"), the actual HBN in the name. The route keys on the load: `GET /admin/uploads/wet_weights/<load id>.csv`, the attachment `<HBN>(n).csv`. The file's rows are that load's only, by today's three rules applied to the one load: its pasted tags (one row per tag, the load's wet total split across them by the jitter law, seeded by the batch and the load so a re-download reproduces it), else its plant count, else its scale reads. HarvestName stays the HBN; the barn stays the DryingLocation; ActualDate reads the load's `effective_date`, else the farm day of its `created_at`, never `updated_at`. The header, the columns, the weights' precision and the jitter law do not change.
3. THE PENDING LAW PER LOAD. A finished, non-voided load pends its own file until its own mark (`metrc_uploads` kind `wet_weights`, `ref_id` the load's id, `harvest_batch_id` its batch, `filename` `<HBN>(n).csv`), an existence kind like the package files: a later load, an edit, an unload or a trim never re-pends it. A batch-level mark (`ref_id` NULL, every mark made before this brief) covers each load of its batch created before the mark. Mark uploaded, Mark the checked uploaded (items `wet_weights:<load id>`), Clear all and the sheet sync's pending harvest file (every pending `<HBN>(n).csv` of the batch, joined with ", ") read this one predicate (canon 0.30.5: the list and the mark read one predicate).
4. THE TAGS PER LOAD (his word: "Paste tags per load"). A new column `harvest_plant_tags.wet_weight_entry_id`. Each pending load's row carries its own tag box, saving replaces that load's tags as today's save replaces a batch's, each row logged; a tag already held by another live load is refused with that load's file named; once the load's file is marked, its tags are read-only. The migration sets the load on every live tag of a batch with exactly one non-voided load; tags on a batch with two or more loads stay unassigned, ride no file, and the batch's load rows say how many are unassigned until a hand pastes them on a load.
5. CHANGED AFTER UPLOAD (his word: "Flag it, no re-pend"). The mark records the load's wet total and plant count the file carried (two new columns on `metrc_uploads`). A load whose current wet total or plant count differs from its latest mark's shows under a new section of Pending Data Uploads, Changed after upload: the file, when it was marked, the grams and count then and now, and the difference. Acknowledge (a reason, logged) records the current values as the load's new baseline and cuts no file, the reconcile note's shape. No harvest file re-pends for it. A load covered only by a batch-level mark has no baseline and is not flagged.
6. THE LOAD'S OTHER FILES CARRY ITS (n) (his word: "Yes, match the (n)"): `location_change_<HBN>(n)_<silo>_<yyyymmdd>.csv`, `packages_from_harvests_<HBN>(n).csv`, `package_adjustments_<HBN>(n).csv` (the unload's and the trim reconcile's), the marks' filenames the same; the Package files rows show the file's name where they show the HBN. Their contents do not change.
7. THE PAGE. Pending Data Uploads, Wet Weights: one row per pending load, reading the file `<HBN>(n).csv`, the Lot, the load (its truck or its space), its wet total, its plant count, its tags (the count and the box), the last activity, Download and Mark uploaded. Spanish beside every new word.
8. NOTHING ELSE MOVES: the METRC columns, the barn rule, the jitter law, the count rule, the package files' contents, every other upload kind, the ledger, the clocks, Silo Ops.
9. THE TESTS. One HBN over two loads: (1) pends alone with load 1's rows; marked; load 2's finish pends only (2), with load 2's rows; an unload, a trim status move and an edit never re-pend (1); an edit to (1)'s grams after its mark shows under Changed after upload with the difference, and Acknowledge clears it; a lone load reads (1); tags pasted on each load ride only their own file, a tag held by the other load is refused, the box is closed after the mark; the three backfills (numbers, tags on a one-load batch, none on a two-load batch); a batch-level mark covering its old load; ActualDate from `effective_date` on a file downloaded after the load's unload; the location change and unload names with (n); Mark the checked and Clear all per load; the sheet sync's names. `scripts/smoke.mjs`: a lot finished as two truck loads, `<HBN>(1).csv` and `<HBN>(2).csv` each with its own rows and its own tags, (1) marked, (1)'s grams edited and seen under Changed after upload, acknowledged; the two loads' location change and unload files named apart.
