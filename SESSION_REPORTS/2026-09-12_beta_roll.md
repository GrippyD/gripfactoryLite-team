# Session report: THE BETA ROLL AND THE SEED SNAPSHOT (canon 0.30.53), Scribe-direct, 2026-09-12

**Scribe:** Gripfactory Lite Scribe (Cowork), Scribe-direct under G-2. An ops slice: two owner-run Node scripts and a shared helper, a CLAUDE.md paragraph. No app code, no migration. The roll itself waits for the owner's keyboard.

## The owner, verbatim (from the road)

"Let's roll the db one last time and then take a snapshot of all seed data  (including the settings in the admin toggles that don't get rolled.  I'm about to release this for the true beta test)"

## Why it waits for a keyboard

The roll begins with `wrangler d1 create`, which is not one of the road lane's steps (canon 0.30.51: tsc, tests, an optional probe and migrations apply, the deploy), and the running watcher cannot learn a new step without being restarted at the keyboard. Both need the owner at the laptop for one command, so the roll is written as that one command and everything around it is prepared and committed now.

## What shipped

**`app/scripts/roll-beta.mjs`** (one command from `app\`: `node scripts\roll-beta.mjs`), stopping at the first red step:

1. Reads the grip database from `wrangler.toml` (THE NAME LAW FOR DEPLOYS) and probes it with `SELECT 1` (the destructive-runbook law: a flake dies before anything runs).
2. **The pre-roll snapshot:** every table of the current database dumped to `db_backups/<stamp>_pre_roll_<name>/<table>.json` with a `_manifest.json` of row counts and a copy of the toml. `wrangler d1 export` fails under the OAuth login (MEMORY, 2026-09-06), so the dumps ride `d1 execute --remote --json`, one table at a time, as the purge runbook's backups did. This is the alpha's last picture and the source of the settings carried below.
3. Creates `gripfactory-lite-grip-<today>` beside the old database (the old one stands until the owner's own word deletes it), reading the new id from wrangler's output.
4. Patches the env.grip d1 block of the toml to the new name and id (every other byte kept, CRLF included), probes the new database, applies migrations 0001 through the head from zero, deploys the worker so the binding points at the new database. A red step here restores the toml before stopping.
5. **Carries the seed tables:** `app_config` (the admin toggles: the PIN, the jitter, the yield, the extraction codes, the audit interval), `lookup_values` (every Admin lookup: licenses, locations, field locations, internal fields, listing categories, sign-offs and the rest), `farms`, `strains`, `grow_methods`, `package_types`, `dry_spaces`, `label_templates`, `suppliers`, `equipment_assets`, `equipment_pm_schedules`, `people` are made to read exactly as the pre-roll snapshot (DELETE, then INSERT in batches of 20 rows, literals inlined, under D1's statement caps), so what the owner set in Admin survives the roll. Every other table starts empty: lots, wet weights, packages, moves, silo loads, the METRC mirror and its mounts, the Zoho listings and mounts, orders, tests, tickets, imports, the change log.
6. **The beta seed snapshot:** every table of the new database dumped to `db_backups/<stamp>_beta_seed_<newname>/`, with the toml after the roll and the `_carry.sql` that ran (in the pre-roll folder). This is the baseline of the true beta: what the floor looked like the moment it opened.
7. Verifies: each carried table's count equals the pre-roll count, every other table reads zero; writes `DEPLOY/roll-result.json` (old and new database, migrations, version id, the two folders, the counts, any mismatch) for the Scribe to stage back and fold, and prints the same summary.

**`app/scripts/db-snapshot.mjs [label]`**: the snapshot alone, any time (`node scripts\db-snapshot.mjs beta_week1`), same folder shape.

**`app/scripts/d1lib.mjs`**: the shared pieces (the toml reader and patcher, the shell runner, `d1Query` through `--json`, `d1File`, `listTables`, `dumpAll`, `carrySql`). The pure pieces (toml read and patch, the carry SQL with its quoting) are proven here in the sandbox: the patch changes exactly the two values and nothing else, c10 and local untouched; the carry SQL doubles single quotes and writes NULLs.

**`CLAUDE.md`** names both scripts as the owner's alone.

## Flags

The carry replaces the seed tables wholesale from the pre-roll dump: if a future migration re-seeds one of them with `INSERT OR IGNORE`, the carried rows win and the migration's new rows still land. `people` is carried as settings (roles and names), not as history; the owner can say otherwise. The pre-roll dump of a large METRC mirror (tens of thousands of plants) rides one `SELECT *` per table through wrangler; a very large table that fails to dump stops the roll before anything is created, by design.
