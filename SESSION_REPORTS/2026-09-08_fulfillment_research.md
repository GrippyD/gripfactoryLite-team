## 2. What SalesHelper says (the live upstream of our [SalesHelper] tile)

- **Flow (CANON section 1)**: Zoho Inventory Items export → collapsed menu → the salesperson's single-file order form → (a) printable receipt, (b) a Zoho-importable Sales Order CSV, (c) an order-record JSON; logistics imports the CSV into Zoho Inventory.
- **Allocation (section 5)**: an order line is filled oldest package first (FIFO by ascending METRC tag), so one line becomes several CSV rows, one per package.
- **The outbound CSV (section 7)**: 13 columns: SalesOrder Number, Order Date, Customer Name, Sales Person, Sales Channel (always direct_sales), Item Name, SKU (the METRC tag), QuantityOrdered, Item Price, Item Total, CF.Customer License #, CF.Destination License #, CF.Origin License #. Location Name is deliberately omitted. Lesson from the first live import (2026-08-31, SH-20260831-PQAS → Zoho SO b21760c5166): Zoho assigns its own SO number; the SH- number does not survive, so duplicate protection by number is nil.
- **The revision precedent (orders/incoming/REVISION-NOTE-SH-20260831-PQAS-R1.md)**: stale menu data allocated packages that were gone; Zoho flagged the SO "needs backordering"; the fix was a rebuilt order (R1) against packages verified in stock, imported, with the original voided; logistics adds a CRIF fee line manually in Zoho. A pick that finds a package missing is a known, named failure.
- **Zoho's own Sales Orders export (data/so_history/Sales_Order_8.csv, 1,165 orders, 11,844 line rows, 252 customers)**: 96 columns, one row per line item. Status is confirmed or invoiced (47 open orders in the file); CF.Status (Internal) runs Submitted → Approved → Shipped; QuantityPacked is zero on every confirmed row (Zoho's pack step is not used); Item.CF.Location Code carries a rack address on 8,988 of 11,844 rows (441 distinct codes, P2.3.A-style shelves plus Oxford N and North Wall; 548 blank); Line Item Location Name is Head Office on three quarters of rows, PNN on 1,006; Usage unit is blank on most rows and otherwise lb / each / Gram / Liter in many spellings; Delivery Method is blank, Motas, or T1; Expected Shipment Date, Sales Person, and the three license custom fields ride every row.

## 2b. What gripfactorish / gripfactorylite says (Code\gripfactorish, June and July 2026: THE iteration)

This is the morning-readout tool that graduated from one HTML file (reference/gripfactorish.html, v0.3.5) into the gripfactorylite repo (TypeScript front end, Postgres schema draft). Its "Stage Raw Data" drop is where SOs mount, and its pipeline is where picking lives.

- **The mount.** A dropped file is recognized as a Zoho Sales Order export by filename (`sales_order`) or by columns (`Product Sub` or `Status (Internal)` present); csv or xlsx. `parseZoho` walks the line rows: a line is bucketed into one of the ten readout categories by `Item.CF.Product Sub` through `ZOHO_SUB_MAP` (thca → THCA before anything else; bulk flower → BUD; prepack ounces or max out bags → PREPACK; vape or cart → VAPES; infused pre-rolls → PREROLLS; infused flower → INFUSED BUD; concentrate → DISTILLATE; shake → SHAKE; trim → TRIM); lines whose sub matches `crif|processing` are ignored (the CRIF fee line and processing lines never count); a line with no sub or no match is ignored and counted as such. The SO number is `SalesOrder Number` (fallbacks: Sales Order Number, SO Number, SalesOrder ID, Order Number). Quantities are `QuantityOrdered` and `QuantityInvoiced` in the category's native unit (lb for the weight categories, each for pre-rolls and vapes, liters for distillate), never re-converted.
- **The status vocabulary is Zoho's `CF.Status (Internal)`**, lowercased: `SO_STATUSES = ['submitted','approved','picking','fulfilled']`, with `shipped` on top. The app keeps, per category and per status, a Set of distinct SO numbers and a quantity accumulator; the readout maps approved to Accepted, submitted to Submitted, shipped to Shipped (shipped counts `QuantityInvoiced` inside the season window, 10/1 of the prior year onward, and METRC Transfers trump Zoho for shipped).
- **Shipping Today** = lines whose `Expected Shipment Date` is today (distinct SOs plus ordered quantity), with the hand-keyed webform count overriding the order count when an operator entered one.
- **The pipeline table (SLICE-001, v0.3.5)**: rows Shipping Today, Accepted, Submitted, Picking, Fulfilled, times the ten categories plus TOTAL; two rows per status (distinct orders, then quantity in the display unit); TOTAL orders is the union across categories so a multi-category order counts once. Picking and Fulfilled render grayed with a dot "until Zoho starts carrying those statuses"; the export at the time carried only Submitted, Approved, Shipped. The SO Status Detail table shows the same Sets per status.
- **The store (db/migrations/0001_gripfactorish_foundation.sql)**: `sales_order_lines(import_id, so_number, order_date, expected_ship, status_internal, product_sub, readout_category, quantity_ordered, quantity_invoiced)` with an index on so_number; the schema comment spells the lifecycle `submitted | approved | picking | fulfilled | shipped`.
- **Ground rules there (2026-07-01)**: Postgres, TypeScript, never ship ahead of IT; the app must run on METRC alone (the inventory manager's personal sheets are never an upload). "gripfactorylite is deliberately the LITE sibling of gripfactory (the real Plato MRP at Code\gripfactory, v7 rebuild)"; that folder is not connected to this session and was not read.

So the answer to "how Mount SOs should behave" is already written there: mounting is dropping the Zoho export, bucketing lines by Product Sub, and reading the order's own status field. "Pick orders" are the Picking stage of that lifecycle: an order the warehouse has taken from Approved and not yet marked Fulfilled. What gripfactorish never had, because it was stateless and read-only, is the write side: something that moves an order into Picking, produces the pick paper, and moves it to Fulfilled.

## 4. The Scribe's reading of how the two tiles should behave

**Mount SOs** carries gripfactorish's Stage Raw Data drop into Practical, made durable. Dropping the Zoho Sales Order export (csv or xlsx, recognized by name or by its Product Sub / Status (Internal) columns) mounts every line into `sales_order_lines`-shaped rows keyed by the Zoho SO number (customer, order and expected-ship dates, Zoho status, CF.Status (Internal), salesperson, the three licenses, delivery method; per line the item, SKU tag, quantities ordered and invoiced, native unit, price, Product Sub, the readout category by ZOHO_SUB_MAP, and the rack code). CRIF and processing lines are ignored as gripfactorish ignores them. A re-mount of a newer export updates statuses in place; nothing duplicates and nothing writes back to Zoho (section 7.5's pull direction, by CSV under the 0.12.0 law). The mounted page shows gripfactorish's two readouts, the Sales Pipeline (Shipping Today, Accepted, Submitted, Picking, Fulfilled by category, distinct orders and quantity) and the SO Status Detail, so the morning readout moves into the app the crew already opens. SalesHelper's outbound CSV can mount early under its SH- number and match its Zoho twin by customer, date and lines when the export lands.

**Pick Orders** is the write side gripfactorish never had. The Picking column that has sat grayed since July fills from here: the pane lists Approved orders (Zoho's internal status), the pick opens the pick sheet, one line per package tag with item, quantity and unit, grouped by rack address in walking order (P1 before P2, shelf A before B), the customer, licenses, salesperson and expected ship date in the header; taking the pick moves the order to Picking on our side. The picker checks lines off with the picked quantity; a missing package is flagged, never blocking (the overissue law's cousin), and the R1 revision precedent applies. Completing records the picker (a sign-off name) and the date, moves the order to Fulfilled on our side, and hands the picked packages to the ship-external manifest lane addressed to CF.Destination License #, so the METRC paper is cut from the pick rather than retyped. Zoho keeps its own CF.Status (Internal); our Picking and Fulfilled are ours until a lane back to Zoho exists (a fork below).

## 5. Forks for the owner (nothing builds until these are ruled)

gripfactorish already settled several that the first draft of this report left open: the file is Zoho's Sales Order export recognized by name or columns; lines bucket by Product Sub through ZOHO_SUB_MAP; CRIF and processing lines are ignored; Shipping Today is Expected Shipment Date equals today with the webform override; the status vocabulary is Zoho's CF.Status (Internal). What remains:

1. **The Zoho status round trip:** our Picking and Fulfilled stay internal (Zoho's column keeps reading Approved until logistics moves it by hand), or the app pends a status CSV for logistics to import, or the Zoho API when IT's checklist lands (the 2026-05-12 directive).
2. **Where the pick location comes from:** Zoho's Item.CF.Location Code (on three quarters of lines today) now, and our ledger once finished goods and their rack addresses land in it; or the ledger only, which means the FG node first.
3. **What completing a pick does beyond status:** the pick paper only; or also cut the external manifest to the destination license from the picked packages (the ship-external lane exists).
4. **Shortages:** flag only; or offer a same-item substitute from the ledger (FIFO) and pend a revision CSV for logistics, the R1 precedent made routine.
5. **Who signs the pick:** the three sign-off names as they stand, or the warehouse crew added to that lookup.
6. **The paper:** a letter pick sheet, a 4x6 thermal ticket per order (label stock exists in the app), or both.
7. **The marketplace node's internal SOs:** keep as a separate beta concept, retire in favor of mounted Zoho SOs, or make mounting the way a marketplace order becomes real.
8. **The readouts:** carry gripfactorish's Sales Pipeline and SO Status Detail tables into Mount SOs as they stand (the morning readout inside the app), or mount only and leave the readout to the single-file tool.
